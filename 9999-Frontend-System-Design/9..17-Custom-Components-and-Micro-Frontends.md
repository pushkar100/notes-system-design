## Custom Components

In a Tier-1 frontend system design interview, discussing **Web Components** (specifically Custom Elements and the Shadow DOM) demonstrates that you can think outside the boundaries of specific frameworks like React or Angular. You are thinking about browser-native, long-term scalability.

Here is the deep dive into architecting with Custom Components, how the Shadow DOM provides absolute isolation, and the trade-offs involved in enterprise systems.

<!-- TOC --><a name="1-the-concept-history-and-the-need"></a>
### 1. The Concept, History, and The Need

**The History:**
Before modern frameworks, developers relied on jQuery plugins and massive global stylesheets. If Team A wrote a CSS rule for `.btn { background: red; }`, and Team B imported a third-party date picker that also used the `.btn` class, the UI would break. Furthermore, injecting a third-party widget (like a payment button or a chat bubble) into a merchant's website was incredibly risky because the merchant's global CSS and JS could easily bleed into the widget and destroy it.

**The Need & Benefits:**
The W3C introduced Web Components to solve this natively in the browser. It consists of three technologies:
1.  **Custom Elements:** The ability to define your own HTML tags (e.g., `<checkout-button>`) using JavaScript classes.
2.  **HTML Templates:** The `<template>` and `<slot>` tags for defining reusable markup that isn't rendered until asked.
3.  **Shadow DOM:** The absolute encapsulation layer. It creates a hidden, separate DOM tree attached to an element. JavaScript variables and CSS styles inside the Shadow DOM cannot leak out, and external CSS cannot leak in.

**ASCII Diagram: The Shadow DOM Boundary**
```text
========================================================================
                      THE ENCAPSULATION WALL
========================================================================
[ LIGHT DOM (The Host Website) ]
  |
  |-- h1 { color: black; font-size: 24px; }
  |-- <h1>Your Shopping Cart</h1> 
  |
  |-- <secure-checkout>
        |
        |=== #shadow-root (THE WALL) ==================================
        |
        |   [ SHADOW DOM (Isolated) ]
        |     |
        |     |-- <style> h1 { color: blue; font-size: 16px; } </style>
        |     |-- <h1>Pay Securely</h1> 
        |
        ===============================================================
  
*Result:* The host website's `h1` remains black and large. The Shadow DOM's `h1` is blue and small. Neither CSS affects the other.
```

<!-- TOC --><a name="2-basic-setup-and-implementation"></a>
### 2. Basic Setup and Implementation

Implementing a native Web Component requires zero build tools, Webpack, or framework dependencies. It relies entirely on standard ES6 classes.

**Code Snippet:**
```javascript
// 1. Define the class extending the native HTMLElement
class SecureCheckoutButton extends HTMLElement {
  constructor() {
    super(); // Always call super() first

    // 2. Attach the Shadow DOM to this element
    // 'mode: open' means external JS can still inspect it via element.shadowRoot
    // 'mode: closed' denies all external access (rarely recommended)
    this.attachShadow({ mode: 'open' });
  }

  // 3. Lifecycle method: Fired when the element is inserted into the DOM
  connectedCallback() {
    this.render();
    this.setupListeners();
  }

  render() {
    // 4. Inject encapsulated HTML and CSS directly into the shadow root
    this.shadowRoot.innerHTML = `
      <style>
        /* This CSS is trapped here. It will never leak. */
        .btn {
          background: #003087;
          color: white;
          padding: 12px 24px;
          border-radius: 4px;
          border: none;
          cursor: pointer;
          font-weight: bold;
        }
        .btn:hover { background: #001c52; }
      </style>
      <button class="btn">
        <slot name="icon"></slot> <!-- Allows consumers to inject custom icons -->
        Complete Payment
      </button>
    `;
  }

  setupListeners() {
    const btn = this.shadowRoot.querySelector('.btn');
    btn.addEventListener('click', () => {
      // Dispatch a custom event that bubbles up to the Light DOM
      this.dispatchEvent(new CustomEvent('payment-initiated', { 
        bubbles: true, 
        composed: true // Required for events to pierce the Shadow DOM wall
      }));
    });
  }
}

// 5. Register the element with the browser (Name MUST contain a hyphen)
customElements.define('secure-checkout-btn', SecureCheckoutButton);
```

**Usage in HTML:**
```html
<!-- Any framework (React, Vue, Angular) or Vanilla JS can use this natively -->
<secure-checkout-btn>
  <span slot="icon">🔒</span>
</secure-checkout-btn>
```

<!-- TOC --><a name="3-when-to-use-the-enterprise-special-cases"></a>
### 3. When to Use (The Enterprise Special Cases)

In a system design interview, propose Web Components for these specific architectural challenges:

*   **Company-Wide Design Systems:** If your company has 100 teams, some using React, some using Vue, and some maintaining legacy Angular apps, building a single UI component library (Buttons, Modals, Inputs) in React forces everyone else to write wrappers. Building the Design System in native Web Components means *every* framework can consume it instantly.
*   **Embedded Third-Party Widgets:** If you are designing an embedded chat widget, a commenting system, or a third-party checkout button meant to be dropped into thousands of unpredictable merchant websites, you *must* use the Shadow DOM. It is the only way to guarantee the merchant's poorly written global CSS won't distort your widget.
*   **Microfrontends:** When stitching together a host application from different teams using different tech stacks, Web Components serve as a perfect framework-agnostic wrapper to mount the remote applications into.

<!-- TOC --><a name="4-when-not-to-use-the-overkill-cases"></a>
### 4. When NOT to Use (The Overkill Cases)

*   **Standard Single Page Applications (SPAs):** If your entire team is building a dashboard in React, and you have no intention of sharing these components with a non-React team, do not use Web Components. React's component model (along with CSS Modules or Tailwind for scoping) is vastly superior for managing complex data flows, state, and re-renders.
*   **Highly Dynamic, Data-Heavy UIs:** Native Web Components do not have a built-in virtual DOM or declarative state management. Updating a list of 1,000 items requires you to manually write `document.createElement` and `appendChild` logic, or pull in a lightweight wrapper library like `Lit`.
*   **Server-Side Rendering (SSR) Heaviness:** Historically, standard Web Components struggled heavily with SSR because the Shadow DOM relies on JavaScript to attach. (Though Declarative Shadow DOM is slowly fixing this, it is still complex compared to Next.js or Nuxt).

<!-- TOC --><a name="5-architectural-trade-offs-debugging"></a>
### 5. Architectural Trade-offs & Debugging

Building with Shadow DOM introduces unique system constraints that you must plan for.

<!-- TOC --><a name="a-debugging-the-shadow-dom"></a>
#### A. Debugging the Shadow DOM
When an element is hidden in the Shadow DOM, standard global queries fail. 
*   `document.querySelector('.btn')` will return `null`. 
*   To debug or select it via JS, you must explicitly traverse the shadow tree: `document.querySelector('secure-checkout-btn').shadowRoot.querySelector('.btn')`.
*   **In Chrome DevTools:** The elements are hidden by default inside a grey `#shadow-root` drop-down. You must manually expand it to inspect the trapped HTML.

<!-- TOC --><a name="b-the-styling-penetration-problem"></a>
#### B. The Styling Penetration Problem
If the Shadow DOM completely blocks CSS, how does a consumer customize the button to match their brand? You must intentionally open specific "doors" in your encapsulation.
*   **CSS Variables:** Shadow DOM respects CSS Custom Properties. If you write `background: var(--btn-color, blue);` inside the shadow root, the host website can define `--btn-color: red;` in their global CSS, and it will pierce the boundary.
*   **The `::part` Pseudo-element:** You can expose specific elements for styling by adding a `part` attribute. 
    *   *Inside component:* `<button part="submit-btn">`
    *   *Host CSS:* `secure-checkout-btn::part(submit-btn) { border-radius: 10px; }`

<!-- TOC --><a name="c-event-retargeting"></a>
#### C. Event Retargeting
When an event (like a click) fires inside the Shadow DOM and bubbles up to the Light DOM, the browser intentionally masks the exact target to maintain encapsulation.
*   If a user clicks the internal `<button>`, any event listener on the `document` will think the click originated from the `<secure-checkout-btn>` host tag itself, not the button inside it. You must architect your events carefully using `composed: true` to allow them to escape.

## Micro Frontends

In the early 2010s, backend engineering underwent a massive revolution: **Microservices**. Backend teams chopped up massive, monolithic servers into small, independent services. 

However, the frontend didn't evolve. It became a **"Frontend Monolith."** You had 50 frontend engineers working in a single React repository, stepping on each other's toes, breaking each other's builds, and waiting in a 45-minute CI/CD pipeline queue just to fix a typo.

**Microfrontends (MFE)** apply the microservices philosophy to the browser. It is an architectural style where a single, cohesive web application is composed of independently deliverable frontend applications.

<!-- TOC --><a name="the-evolution-monolith-to-microfrontend"></a>
### The Evolution: Monolith to Microfrontend

**ASCII Diagram: The Architectural Shift**
```text
========================================================================
                      1. THE FRONTEND MONOLITH
========================================================================
[ FRONTEND REPO ] (Team A, Team B, Team C all commit here)
      |
      v
[ BACKEND E-COMMERCE ]  [ BACKEND USER ]  [ BACKEND INVENTORY ]
(Microservices)         (Microservices)   (Microservices)

========================================================================
                      2. MICROFRONTENDS
========================================================================
[ PRODUCT UI ]         [ CART UI ]        [ PROFILE UI ]
 (Team A Repo)          (Team B Repo)      (Team C Repo)
      |                      |                  |
      v                      v                  v
[ BACKEND E-COMMERCE ]  [ BACKEND USER ]  [ BACKEND INVENTORY ]
```

**The Need:**
1.  **Scale:** Allow multiple teams to work concurrently without a centralized release manager.
2.  **Tech Agnosticism:** Allow Team A to use React, while Team B slowly migrates legacy code from Angular, without rewriting the whole app.
3.  **Independent Deployments:** The "Cart" team can deploy a bug fix in 2 minutes without re-compiling the "Product Catalog" code.

<!-- TOC --><a name="modern-ways-to-implement-microfrontends"></a>
### Modern Ways to Implement Microfrontends

There are three primary ways to architect this today. In a Tier-1 system design interview, **Webpack Module Federation** is the absolute gold standard you must discuss.

<!-- TOC --><a name="1-webpack-module-federation-the-modern-gold-standard"></a>
#### 1. Webpack Module Federation (The Modern Gold Standard)
Introduced in Webpack 5, this allows a JavaScript application to dynamically load code from *another* completely separate build at runtime. It is not an Iframe; it shares the same DOM and memory.

**ASCII Diagram: Module Federation**
```text
[ HOST APP (App Shell) ]
  |-- Loads React
  |
  |-- Encounters <CartRemote /> 
  |-- (Network Request: GET https://cart-team.com/remoteEntry.js)
  v
[ CART APP (Remote) ]
  |-- Exposes the <Cart> component
  |-- (Module Federation notices the Host already loaded React, 
       so it skips downloading React a second time!)
```

**Code Snippet:**
```javascript
// Cart Team's webpack.config.js (The REMOTE)
const ModuleFederationPlugin = require('webpack/lib/container/ModuleFederationPlugin');

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'cartApp', 
      filename: 'remoteEntry.js', // The file the host will request
      exposes: {
        './CartWidget': './src/components/CartWidget', // Exposing a specific React component
      },
      shared: ['react', 'react-dom'], // Tells Webpack: "Share these libraries if the host has them"
    }),
  ],
};

// Host Team's App.jsx (The HOST)
import React, { Suspense } from 'react';

// Dynamically import the code from the other server at runtime!
const RemoteCartWidget = React.lazy(() => import('cartApp/CartWidget'));

const AppShell = () => (
  <div>
    <h1>Main E-Commerce Site</h1>
    <Suspense fallback={<div>Loading Cart...</div>}>
      <RemoteCartWidget /> 
    </Suspense>
  </div>
);
```

<!-- TOC --><a name="2-web-components-the-framework-agnostic-way"></a>
#### 2. Web Components (The Framework Agnostic Way)
If you have teams using vastly different tech stacks (React, Vue, Svelte), Module Federation gets tricky because sharing dependencies is hard. Instead, teams compile their code into native HTML Custom Elements.

**Code Snippet:**
```javascript
// Team Vue compiles their app into a standard HTML Web Component
class CheckoutButton extends HTMLElement {
  connectedCallback() {
    this.innerHTML = `<button>Checkout (Vue inside!)</button>`;
  }
}
customElements.define('checkout-btn', CheckoutButton);

// Team React uses it like a normal div
const App = () => (
  <div>
    <checkout-btn></checkout-btn> 
  </div>
);
```

<!-- TOC --><a name="3-iframes-the-legacysecure-way"></a>
#### 3. Iframes (The Legacy/Secure Way)
The oldest method. You embed Team B's app inside Team A's app using an `<iframe>`. 
*   **Pros:** Absolute 100% isolation. No CSS or JS collisions possible. Perfect for embedding highly sensitive third-party apps (like Stripe payment fields).
*   **Cons:** Terrible UX, poor accessibility, impossible to share data easily, and high memory usage (loads the browser engine multiple times).

<!-- TOC --><a name="special-cases-when-you-should-use-microfrontends"></a>
### Special Cases: When You SHOULD Use Microfrontends

1.  **Conway's Law dictates the Architecture:** You have 50+ frontend developers split across 5 autonomous domains (e.g., Spotify: "Search Team," "Player Team," "Playlist Team"). Each team has its own Product Manager, Backend, and Frontend.
2.  **Incremental Tech Migrations:** You have a massive 5-year-old application built in Angular. The business wants to move to React. A "Big Bang" rewrite will stall feature development for a year. With MFEs, you wrap the Angular app in a Host shell, and write all *new* features as React Remotes.
3.  **Massive Enterprise Dashboards:** Applications like the AWS Console. When you click from EC2 to S3, you are seamlessly transitioning between completely different frontend applications managed by different organizations.

<!-- TOC --><a name="overkill-when-you-should-never-use-microfrontends"></a>
### Overkill: When You Should NEVER Use Microfrontends

Microfrontends solve *organizational* scaling problems, not *technical* scaling problems. 

1.  **Startups & Small Teams (<= 15 devs):** Do not use MFEs. You will spend 40% of your engineering time fighting Webpack configurations and CI/CD pipelines instead of building features. Use a Monolith (or a Monorepo using Turborepo/Nx).
2.  **Highly Synchronized UIs:** If clicking a button in Component A requires a highly complex, 60-fps animated transition into Component B, MFEs will fail. MFEs are meant for loosely coupled features.
3.  **Strict Performance Constraints:** If your app is a consumer-facing mobile web app where every kilobyte matters, MFEs are risky. You can easily accidentally download multiple versions of dependencies if federation is misconfigured.

<!-- TOC --><a name="the-trade-offs-how-it-affects-regular-app-development"></a>
### The Trade-Offs: How it Affects Regular App Development

If you adopt Microfrontends, daily frontend development fundamentally changes. You must solve three major architectural headaches:

<!-- TOC --><a name="1-state-sharing-the-communication-nightmare"></a>
#### 1. State Sharing (The Communication Nightmare)
In a monolith, you use Redux or React Context. In an MFE, the Header (App A) cannot read the Redux store of the Cart (App B). 
**The Solution:** You must decouple them using standard Browser APIs like `CustomEvents` or a Pub/Sub event bus.

**Code Snippet:**
```javascript
// App B (Cart MFE) dispatches a native browser event
window.dispatchEvent(new CustomEvent('CART_UPDATED', { detail: { count: 5 } }));

// App A (Header MFE) listens for the event
window.addEventListener('CART_UPDATED', (e) => {
  setCartBadgeCount(e.detail.count);
});
```

<!-- TOC --><a name="2-css-collisions"></a>
#### 2. CSS Collisions
If Team A writes `.btn { background: blue; }` and Team B writes `.btn { background: red; }`, and both are loaded via Module Federation into the same DOM, the last one loaded wins.
**The Solution:** Teams *must* use scoped CSS (CSS Modules, Styled Components) or strict naming conventions (BEM) prefixing their team name (e.g., `.team-cart-btn`).

<!-- TOC --><a name="3-testing-complexity"></a>
#### 3. Testing Complexity
How do you run Integration Tests? The Cart team's app might work perfectly in isolation, but when loaded inside the Host app, a CSS collision breaks the layout. 
**The Solution:** You must maintain a complex End-to-End (E2E) testing suite (Cypress/Playwright) that spins up the Host and all Remotes simultaneously in a staging environment to catch integration failures. 

<!-- TOC --><a name="summary"></a>
### Summary

Microfrontends are a heavy architectural hammer. Use them when human communication and deployment bottlenecks are your biggest problems. Avoid them if you just want to organize your code—standard React component architecture is better suited for that.
