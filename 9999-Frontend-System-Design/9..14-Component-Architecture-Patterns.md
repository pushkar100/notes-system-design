In a Tier-1 frontend system design interview, your component architecture demonstrates how you balance **reusability, separation of concerns, and scalability**. If you build a massive application with poorly designed components, you will inevitably encounter "Prop Bloat" (passing 50 props to a single component) and unmaintainable tightly-coupled spaghetti code.

Here is a deep dive into the four most critical component architecture patterns you must know, how they solve these scaling issues, and how to implement them.

## Basic Component Patterns

<!-- TOC --><a name="1-container-presentational-pattern-smart-vs-dumb"></a>
### 1. Container / Presentational Pattern (Smart vs. Dumb)

**The Simple Explanation:**
This pattern splits a component into two distinct parts. 
1. The **Container (Smart)** handles all the business logic: data fetching, state management, and side effects. It has no UI of its own.
2. The **Presentational (Dumb)** handles exactly one thing: rendering the UI based on the props it receives. It knows nothing about APIs or databases.

**ASCII Diagram:**
```text
========================================================================
                      CONTAINER / PRESENTATIONAL
========================================================================

[ BACKEND API ]
      |
      v
[ Container Component (UserListContainer) ]
- Fetches data from /api/users
- Manages loading/error state
- Handles business logic
      |
      | (Passes clean data via Props)
      v
[ Presentational Component (UserListUI) ]
- Pure function of props
- Renders <ul> and <li> 
- NO API calls, NO complex state
```

**Code Snippet:**
```jsx
// 1. The Presentational Component (Dumb)
// Highly reusable. You can easily test this or put it in a Storybook.
const UserListUI = ({ users, isLoading, onUserClick }) => {
  if (isLoading) return <Spinner />;
  return (
    <ul>
      {users.map(user => (
        <li key={user.id} onClick={() => onUserClick(user.id)}>
          {user.name}
        </li>
      ))}
    </ul>
  );
};

// 2. The Container Component (Smart)
// Ties the dumb UI to the actual data source.
const UserListContainer = () => {
  const [users, setUsers] = useState([]);
  const [isLoading, setIsLoading] = useState(true);

  useEffect(() => {
    fetch('/api/users')
      .then(res => res.json())
      .then(data => {
        setUsers(data);
        setIsLoading(false);
      });
  }, []);

  const handleUserClick = (id) => {
    console.log("Navigating to user:", id);
  };

  return <UserListUI users={users} isLoading={isLoading} onUserClick={handleUserClick} />;
};
```

**Pros:** 
* **Testability:** You can unit test the UI component without mocking network requests.
* **Reusability:** The `UserListUI` can be reused with mock data, offline data, or a completely different API endpoint.
**Cons:** 
* Can lead to unnecessary boilerplate for very simple components.

**When to use:** When building complex, data-heavy views. Whenever a component is doing too much UI rendering *and* too much data fetching simultaneously.
**When NOT to use:** For tiny, isolated UI widgets (like a simple `<Button>`) where splitting it into two files provides zero value.

### 2. Compound Components Pattern

**The Simple Explanation:**
Think of the native HTML `<select>` and `<option>` tags. They don't do much on their own, but together they form a cohesive UI. Compound components are a set of React components that implicitly share state (usually via Context) to work together as a single unit, without forcing the user to pass a massive configuration object.

**ASCII Diagram:**
```text
========================================================================
                      COMPOUND COMPONENTS
========================================================================

Instead of "Prop Bloat":
<Tabs config={[{title: 'A', content: '...'}, {title: 'B', content: '...'}]} />

You author a clean, declarative API:
[ <Tabs> (Holds Context State) ]
      |
      |-- [ <Tabs.List> ]
      |         |-- [ <Tabs.Tab id="1"> ]
      |         |-- [ <Tabs.Tab id="2"> ]
      |
      |-- [ <Tabs.Panel id="1"> ]
      |-- [ <Tabs.Panel id="2"> ]
```

**Code Snippet:**
```jsx
import { createContext, useContext, useState } from 'react';

// 1. Create a Context to hold the shared state secretly
const TabsContext = createContext();

// 2. The Parent Component manages the state
export const Tabs = ({ children, defaultActive }) => {
  const [activeTab, setActiveTab] = useState(defaultActive);
  return (
    <TabsContext.Provider value={{ activeTab, setActiveTab }}>
      <div className="tabs-container">{children}</div>
    </TabsContext.Provider>
  );
};

// 3. Child Components consume the state implicitly
Tabs.Tab = ({ id, children }) => {
  const { activeTab, setActiveTab } = useContext(TabsContext);
  const isActive = activeTab === id;
  
  return (
    <button 
      className={isActive ? 'active' : ''} 
      onClick={() => setActiveTab(id)}
    >
      {children}
    </button>
  );
};

Tabs.Panel = ({ id, children }) => {
  const { activeTab } = useContext(TabsContext);
  return activeTab === id ? <div className="panel">{children}</div> : null;
};

// USAGE: Clean, readable, and highly flexible (you can inject a div between tabs if needed).
<Tabs defaultActive="profile">
  <Tabs.Tab id="profile">Profile</Tabs.Tab>
  <Tabs.Tab id="settings">Settings</Tabs.Tab>
  
  <Tabs.Panel id="profile">Profile Content Here</Tabs.Panel>
  <Tabs.Panel id="settings">Settings Content Here</Tabs.Panel>
</Tabs>
```

**Pros:** 
* **Prevents Prop Bloat:** You don't need a single `<Dropdown>` component with 25 props (`showIcon`, `menuPosition`, `highlightColor`). 
* **Inversion of Control:** The developer consuming the component has full control over the layout and ordering of the children.
**Cons:** 
* Slightly heavier to author and requires understanding of React Context.

**When to use:** Building complex UI widgets for a Design System (Accordions, Dropdowns, Menus, Tabs, Modals).
**When NOT to use:** Simple components that only require 1 or 2 props to function.

### 3. Headless Component Pattern (Custom Hooks)

**The Simple Explanation:**
A Headless Component provides all the complex logic, state management, and accessibility attributes, but renders **absolutely nothing** (no DOM elements). It hands you the logic, and you bring your own UI. In modern React, this is almost entirely executed via Custom Hooks.

**ASCII Diagram:**
```text
========================================================================
                      HEADLESS COMPONENT
========================================================================

[ Headless Hook (useToggle) ]
- State: isOpen
- Methods: open(), close(), toggle()
- A11y: aria-expanded
        |
        | (Returns Logic)
        v
[ Any UI you want! ]
  /             \
<Button>       <Switch>       <Accordion>
```

**Code Snippet:**
```jsx
// 1. The Headless Hook (Pure Logic)
const useDropdown = () => {
  const [isOpen, setIsOpen] = useState(false);
  const toggle = () => setIsOpen(p => !p);
  const close = () => setIsOpen(false);

  // Return state, methods, and required accessibility props
  return {
    isOpen,
    toggle,
    close,
    getToggleButtonProps: () => ({
      onClick: toggle,
      'aria-expanded': isOpen,
      'aria-haspopup': 'listbox'
    }),
    getMenuProps: () => ({
      role: 'listbox',
      hidden: !isOpen
    })
  };
};

// 2. The Consumer (Brings their own UI)
const CustomDropdown = () => {
  const { isOpen, getToggleButtonProps, getMenuProps } = useDropdown();

  return (
    <div>
      <button {...getToggleButtonProps()}>Options</button>
      
      <ul {...getMenuProps()} style={{ display: isOpen ? 'block' : 'none' }}>
        <li>Edit</li>
        <li>Delete</li>
      </ul>
    </div>
  );
};
```

**Pros:** 
* **Ultimate Reusability:** You can use the exact same complex logic for a massive desktop dropdown and a tiny mobile bottom-sheet.
* **Future-Proof:** If you decide to migrate from CSS Modules to Tailwind CSS next year, the complex logic remains completely untouched.
**Cons:** 
* High learning curve. Consumers have to write the JSX markup themselves.

**When to use:** Creating highly reusable logic libraries (like `react-table` or `downshift`), or when dealing with complex accessibility (a11y) rules that need to be shared across vastly different UI designs.
**When NOT to use:** When you want to enforce a strict, unchangeable visual design system across an entire company.

### 4. Component Composition (Slot Pattern)

**The Simple Explanation:**
Instead of passing raw data down through 5 layers of components (Prop Drilling), you pass the **actual React Components** as props or children into designated "slots."

**ASCII Diagram:**
```text
========================================================================
                      COMPONENT COMPOSITION (SLOTS)
========================================================================

PROP DRILLING (Bad):
<Layout user={user} theme={theme} navLinks={links} footerData={footer} />

COMPOSITION (Good):
[ <Layout> ]
    |
    |-- Slot (header) --> [ <Header user={user} /> ]
    |-- Slot (sidebar) -> [ <Sidebar links={links} /> ]
    |-- Slot (content) -> [ <MainContent /> ]
```

**Code Snippet:**
```jsx
// 1. The Layout Component (Defines the slots)
const PageLayout = ({ topNav, leftSidebar, mainContent }) => {
  return (
    <div className="layout-grid">
      <header className="top-nav">{topNav}</header>
      <div className="body-wrapper">
        <aside className="sidebar">{leftSidebar}</aside>
        <main className="content">{mainContent}</main>
      </div>
    </div>
  );
};

// 2. The Consumer (Injects components into slots)
// We instantiate the components at the top level, preventing prop drilling!
export const Dashboard = ({ user }) => {
  return (
    <PageLayout 
      topNav={<TopNav user={user} />} 
      leftSidebar={<Sidebar active="home" />}
      mainContent={<DashboardCharts data={[]} />}
    />
  );
};
```

**Pros:** 
* Solves prop drilling immediately without needing Redux or Context.
* Makes layouts highly explicit and easy to read at the top-level route.
**Cons:** 
* Defining too many slots can make the parent component's JSX look extremely heavy.

**When to use:** Global page layouts, generic wrapper components (like a `<Modal body="{...}" footer="{...}" header="{...}"/>`), or whenever you feel the urge to pass a prop down 3+ levels just to reach a nested component.
**When NOT to use:** For deeply integrated data flows where the child component's state must tightly dictate the parent's behavior.

## Patterns for Common Components

To architect a scalable frontend, you must match the right component to the right design pattern. Using the wrong pattern leads to "Prop Drilling" (passing data through dozens of layers) or "God Components" (a single file with 2,000 lines of code).

Here is the breakdown of the foundational frontend patterns, followed by how to apply them to every major component on a web page.

<!-- TOC --><a name="the-5-core-component-patterns-explained"></a>
### The 5 Core Component Patterns Explained

Before diving into the components, here is a brief primer on the patterns we will use.

**1. Composition (Slots)**
*   **Concept:** Instead of passing data down, you pass fully rendered React components into "slots."
*   **Best for:** Layouts.
```text
[ <Layout> ]
  |-- Slot (header) --> [ <Header /> ]
  |-- Slot (content) -> [ <Main /> ]
```
```jsx
const Layout = ({ header, content }) => <div>{header}<main>{content}</main></div>;
```

**2. Compound Components**
*   **Concept:** Multiple components work together to form a single UI, sharing hidden state (via Context) so you don't have to pass endless configuration props.
*   **Best for:** Complex interactive widgets.
```text
[ <Select> (holds state) ]
  |-- [ <Select.Option value="1"> ]
```
```jsx
<Menu>
  <Menu.Trigger>Open</Menu.Trigger>
  <Menu.List><Menu.Item>Settings</Menu.Item></Menu.List>
</Menu>
```

**3. Container / Presentational (Smart vs. Dumb)**
*   **Concept:** The "Container" fetches data and handles logic. It passes clean data to the "Presentational" component, which only renders the UI.
*   **Best for:** Data-heavy sections.
```text
[ Container (Fetches /api/users) ] ---> Passes data ---> [ UI Component (Renders list) ]
```
```jsx
const UserListContainer = () => {
  const data = useFetch('/users');
  return <UserListUI users={data} />;
};
```

**4. Headless Hooks**
*   **Concept:** You extract 100% of the complex logic into a Custom Hook that returns state and functions. It renders no UI, leaving the visual design entirely up to the consumer.
*   **Best for:** Heavy behavioral logic independent of design.
```text
[ useToggle() Hook ] ---> Returns { isOpen, toggle } ---> Used in <AnyUIYouWant>
```
```jsx
const { isOpen, toggle } = useDropdownLogic();
return <button onClick={toggle}>Menu</button>;
```

**5. Polymorphic / Pure Presentational**
*   **Concept:** "Dumb" primitives that rely entirely on props to look a certain way. Polymorphic components can change their underlying HTML tag (e.g., rendering a Button as an `<a>` tag).
*   **Best for:** Design system base elements.

### Component Architecture Breakdown

<!-- TOC --><a name="group-1-the-layouts-pattern-composition-slots"></a>
#### Group 1: The Layouts (Pattern: Composition / Slots)
These components organize the page. They shouldn't care about the data they hold.

**1. App Shell**
*   **Why:** The highest level of your app. If you pass user data here just to get it to the Navbar, you create massive prop drilling. Use slots.
*   **Plausible Props:** `topNav`, `leftSidebar`, `mainContent`, `footer`.
```text
+-----------------------------------+
|             [ topNav ]            |
+-----------+-----------------------+
| [ left    |                       |
|   Sidebar]|    [ mainContent ]    |
+-----------+-----------------------+
```
```jsx
const AppShell = ({ topNav, leftSidebar, mainContent }) => (
  <div className="layout-grid">
    <header>{topNav}</header>
    <aside>{leftSidebar}</aside>
    <main>{mainContent}</main>
  </div>
);
```

**2. Navigation Bar & Sidebar (w/ links)**
*   **Why:** Navbars change drastically based on authentication state. Slots allow you to easily swap a `LoginButton` for a `UserProfile` component without rewriting the Navbar logic.
*   **Plausible Props:** `leftBrandSlot`, `centerSearchSlot`, `rightActionsSlot`.

<!-- TOC --><a name="group-2-complex-ui-widgets-pattern-compound-components"></a>
#### Group 2: Complex UI Widgets (Pattern: Compound Components)
These components have distinct visual pieces that must talk to each other secretly.

**3. Modal Component**
*   **Why:** A modal needs a header, body, and footer. Passing all of these as a single giant configuration prop (`<Modal body="..." footer="..." title="..."/>`) is unreadable.
*   **Plausible Props (Parent):** `isOpen`, `onClose`.
```text
[ <Modal> (State: isOpen) ]
       |-- [ <Modal.Header> ] ---> Title & Close Button
       |-- [ <Modal.Body> ] -----> Main Content
       |-- [ <Modal.Footer> ] ---> Action Buttons
```
```jsx
<Modal isOpen={open} onClose={close}>
  <Modal.Header>Delete Item</Modal.Header>
  <Modal.Body>Are you sure?</Modal.Body>
  <Modal.Footer><button>Confirm</button></Modal.Footer>
</Modal>
```

**4. Dropdown, Tabs + Accordion**
*   **Why:** Exact same reasoning. The `<Tabs>` parent holds the `activeTab` state. `<Tabs.Tab>` triggers the change, and `<Tabs.Panel>` listens to see if it should render.
*   **Plausible Props (Parent):** `defaultActiveTab`, `onChange`.

<!-- TOC --><a name="group-3-data-driven-views-pattern-container-presentational"></a>
#### Group 3: Data-Driven Views (Pattern: Container / Presentational)
These components interact with your backend API.

**5. List View (Product List) & Grid View**
*   **Why:** You want to be able to reuse the `GridUI` for a loading skeleton, an error state, or mock data during testing. The Container handles the network; the Presentational component handles the CSS grid.
*   **Plausible Props (Presentational):** `items`, `isLoading`, `error`, `onItemClick`.
```text
[ ProductGridContainer ] ---> (Fetches data)
         |
         v
[ ProductGridUI ] ---> Renders <div className="grid">
         |---> [ ProductCard ]
         |---> [ ProductCard ]
```

**6. Detail View (Product Detail)**
*   **Why:** The Container reads the URL ID (`/products/123`), fetches the data, and passes it down.
*   **Plausible Props (Presentational):** `productData`, `onAddToCart`.

**7. Forum Post / Comment & Chat Message**
*   **Why:** Comments and threads use a specific sub-pattern: **Recursive Presentational**. The component renders itself, and if it has a `replies` array, it maps over it and calls itself again.
*   **Plausible Props:** `author`, `content`, `timestamp`, `replies`.
```text
[ Comment ID: 1 ]
  |-- [ Avatar ] [ Text ]
  |-- [ Replies ]
        |-- [ Comment ID: 2 ]
              |-- [ Avatar ] [ Text ]
```
```jsx
const CommentThread = ({ comment }) => (
  <div className="comment-box">
    <p>{comment.text}</p>
    {comment.replies && comment.replies.map(reply => (
      <div className="indent"><CommentThread comment={reply} /></div>
    ))}
  </div>
);
```

<!-- TOC --><a name="group-4-heavy-behavioral-logic-pattern-headless-hooks"></a>
#### Group 4: Heavy Behavioral Logic (Pattern: Headless Hooks)
These components are mathematically complex but can look like anything visually.

**8. Search Bar (+ Search Dropdown)**
*   **Why:** A good search requires debouncing the input, managing loading states, caching, and handling keyboard arrows (up/down to select results). Tying this math to a specific HTML `<input>` is restrictive. Extract it to `useSearch()`.
*   **Hook State:** `query`, `results`, `isSearching`, `activeIndex`.
```text
[ useSearch(apiEndpoint) ]
  |-- Returns: query, results, handleKeyDown()
  v
[ SearchUI ] ---> Uses the data to render a custom Input and Dropdown.
```

**9. Forms & Form Inputs (Complex)**
*   **Why:** Tracking dirty state, touched state, and validation errors is purely logical. Libraries like React Hook Form (`useForm`) provide the headless logic, and you attach it to your UI inputs.

**10. Free-form Text Editor & Video Player**
*   **Why:** Text editors manage a complex JSON tree of cursors and nodes. Video players manage HTML5 media APIs (`currentTime`, `duration`, `volume`). A `useVideoPlayer` hook handles the math, letting you build any custom play button you want.

<!-- TOC --><a name="group-5-ui-primitives-pattern-polymorphic-pure-presentational"></a>
#### Group 5: UI Primitives (Pattern: Polymorphic / Pure Presentational)
These sit at the bottom of the tree. They fetch no data and have no complex logic.

**11. Buttons**
*   **Why:** A button needs to look consistent across the app, but sometimes it needs to act like a `<button>` (submitting a form) and sometimes like an `<a>` (navigating). The Polymorphic pattern handles this using an `asChild` or `component` prop.
*   **Plausible Props:** `variant`, `size`, `disabled`, `leftIcon`, `as`.
```jsx
// Renders an actual <button>
<Button variant="primary">Submit</Button>

// Renders an <a> tag styled exactly like a button
<Button variant="primary" as="a" href="/home">Go Home</Button>
```

**12. Component Displaying an Image**
*   **Why:** Purely presentational wrapper around the native `<img>` tag to enforce lazy loading and render a fallback skeleton if the image fails to load.
*   **Plausible Props:** `src`, `alt`, `fallbackSrc`, `aspectRatio`.

**13. Component Holding an Article**
*   **Why:** When receiving a raw string of HTML/Markdown from a CMS, this component's only job is to safely inject it into the DOM and wrap it in a typography class to ensure the fonts and spacing look correct.
*   **Plausible Props:** `htmlContent`, `title`, `date`.
```text
[ <ArticleLayout> ]
  |-- [ Header: Title & Date ]
  |-- [ Typography Container ]
        |-- (Injected raw HTML string)
```
```jsx
const ArticleLayout = ({ title, htmlContent }) => (
  <article>
    <h1>{title}</h1>
    <div 
      className="typography-styles" 
      dangerouslySetInnerHTML={{ __html: htmlContent }} 
    />
  </article>
);
```
